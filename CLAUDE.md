# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

**PixelHero** is a 2D MMORPG: a **Unity client** plus a **C# (.NET 10) game server and hub**. It started as a port of **BrowserQuest**  and is now its own project: it does **not** depend on BrowserQuest. Nothing in the repository runs, reads or compares against the original any more. The code still follows the original's structure, and the regression fixtures were recorded from it (see Architecture). `FEATURES.md` lists the game features that were ported, `HUB_PLAN.md` the hub/HTTP API/leaderboard/password-reset/Discord port (done), and `live.md` the production deployment (`hub.jdj.kr`, `pixelhero.jdj.kr`). All three are in Korean.

**Naming:** the product is PixelHero everywhere: folders, namespaces (`PixelHero.*`), assemblies, env vars (`PIXELHERO_*`), PlayerPrefs keys (`pixelhero.*`), shaders (`PixelHero/...`), the in-game text and the world. Write new code and text with that name. "BrowserQuest" stays only where it credits the original: the credits screen and its link (`IntroView.OriginalUrl`, `credits.port`), the about text, the NPC line about open source, and comments or docs about where something came from. The MongoDB database is `pixelhero` too. The fixtures in `Tools/fixtures/` had the same rename applied.

## Layout

- `Assets/`, `Packages/`, `ProjectSettings/`: the Unity project (Unity **6000.3.26f1**, 2D URP, new Input System, Test Framework, Newtonsoft Json, **Gamma** color space). `Library/`, `*.csproj` and `*.sln` at the root are generated by Unity; never `dotnet build` them.
- `Assets/PixelHero/`: all client code. Assemblies are `PixelHero.Runtime` (namespace `PixelHero`), `PixelHero.Editor`, `PixelHero.Tests.EditMode` and `PixelHero.Tests.PlayMode`.
- `Server/`: the C# port of `packages/server` and `packages/hub` (`PixelHero.Server.slnx`). `PixelHero.Server.Core` is the port, `PixelHero.Server` the SuperSocket 2.1 host, `PixelHero.Hub` the hub, and `tests/PixelHero.Server.Tests` the NUnit tests.
- `PixelHero-Data/`: the game's data, laid out without the original's `packages/` level. `server/data/**` is read by the C# server (`ServerMain.ResetState`), and the hub reads its `mobs.json`. `common/text/profanity.json` is the chat filter. `client/maps/map.json` is the client map, which the importer copies to `Generated/data/map.json`. The folder also holds `.env.defaults` and the deployment samples `.env*.sample`. Both servers find the repository root by looking for `PixelHero-Data/server/data`. Quest drafts that are not in the game yet are in `Docs/quest-drafts/`. They use the `quests/*.json` format, but their NPCs and items do not exist yet. To add a quest, put its JSON in `server/data/quests/` and its key in the list at the top of `Quests.cs`.
- `Tools/serve_webgl.mjs` serves a WebGL build. `Tools/fixtures/` holds only recorded test data: `out/` (expected results), `recordings/`, `sessions/`, `scenes/` and `server/scenarios/*.json` (scenario inputs). The scripts that recorded them from the original (`gen_*.mts`, `harness.mjs`, `build_scenarios.mjs`, `codegen/`, `net/`) were deleted. Comments that still name them only say where a fixture came from.

## Commands

C# server and hub (these are our own projects, so `dotnet` is fine):

```
dotnet build Server/PixelHero.Server.slnx
dotnet test Server/tests/PixelHero.Server.Tests                                   # ~2 min; Mongo contract tests are skipped when the remote DB is unreachable
dotnet test Server/tests/PixelHero.Server.Tests --filter "FullyQualifiedName~ScenarioTests"
dotnet run --project Server/src/PixelHero.Server -- --port 9031 --skipDatabase true   # config: PixelHero-Data/.env.defaults, then .env, then --key value
dotnet run --project Server/src/PixelHero.Hub -- --hubEnabled true                    # WS on HUB_WS_PORT, HTTP on HUB_PORT
```

Unity runs in **batch mode**, which fails while the Editor has the project open, so ask the user to close it first. Check the log for `error CS` and exceptions.

```
UNITY=/Applications/Unity/Hub/Editor/6000.3.26f1/Unity.app/Contents/MacOS/Unity
$UNITY -batchmode -projectPath "$PWD" -runTests -testPlatform EditMode -testResults results.xml -logFile tests.log
$UNITY -batchmode -projectPath "$PWD" -runTests -testPlatform EditMode -testFilter "PixelHero.Tests.GameVersionTests" -testResults results.xml -logFile tests.log
$UNITY -batchmode -projectPath "$PWD" -runTests -testPlatform PlayMode -testResults play.xml -logFile play.log
$UNITY -batchmode -quit -projectPath "$PWD" -executeMethod PixelHero.Editor.CatalogBuilder.RebuildBatch -logFile catalog.log   # import settings + SpriteCatalog.asset
$UNITY -batchmode -quit -projectPath "$PWD" -executeMethod PixelHero.Editor.GameSceneBuilder.BuildBatch -logFile scene.log    # rewrites Scenes/Game.unity
$UNITY -batchmode -quit -projectPath "$PWD" -executeMethod PixelHero.Editor.WebGLBuilder.BuildBatch -logFile webgl.log        # Builds/WebGL (~7 min)
node Tools/serve_webgl.mjs [9050] [--https]   # serve the build; ?server=ws://host:port, ?hub=http(s)://host:port
```

The `unity` CLI (unity-cli skill / Unity MCP) can also drive a running Editor.

EditMode tests read game data through `TestPaths.Data(...)` and recorded fixtures through `TestPaths.Fixtures`/`Recordings`. `LiveServerTests`/`LiveGameTests` (PlayMode) are ignored when no server is running. They use the PORT in `PixelHero-Data/.env`, or `PIXELHERO_SERVER_URL` (e.g. `ws://127.0.0.1:9031`).

The committed `Assets/PixelHero/Generated/` is the source of the sprites, tilesets, fonts, audio, `sprites.json` and the region data. To change an asset, add, replace or remove it there with its .meta. Then run `CatalogBuilder.Rebuild` (menu **PixelHero/Rebuild Sprite Catalog**): it applies the import settings, copies `PixelHero-Data/client/maps/map.json` to `Generated/data/map.json`, and rewrites `SpriteCatalog.asset`.

## Architecture (big picture)

**Regression fixtures.** The fixtures in `Tools/fixtures/` were recorded from the original PixelHero: it ran on virtual timers with a seeded `Math.random` (Park–Miller). They pin the current behaviour byte for byte.
- The client gets entity, text, audio and overlay replays (`EntityReplayTests`). The server gets packet-frame scenarios (`ScenarioTests`, plus `ClusterScenarioTests` for the hub with several servers).
- They can no longer be regenerated. A change that alters behaviour on purpose (game rules, data, text) must update the affected expected output in `Tools/fixtures/out/` in the same change, after checking the diff is exactly the intended one.
- A test that fails without an intended change is a regression.

**JS semantics layer (`Scripts/Runtime/Js/`)**, shared by client and server. `PixelHero.Server.Core.csproj` links `JsJson.cs`, `JsNumber.cs`, `JsValue.cs`, `Fdlibm.cs` and `Common/Generated/*.cs` from `Assets/`. Edit those only under `Assets/`, and keep them compiling in both Unity and .NET.
- `JsNumber` converts between decimal strings and doubles exactly. Mono's `double.Parse` is not correctly rounded, so never use it for wire numbers.
- `Fdlibm` gives V8-exact sin/cos/atan2. Never use `Math.Sin/Cos/Atan2` for values the original computes.
- On the server, `JsObject` keeps JavaScript key order, and `EventLoop`/`Node` provide setTimeout, setImmediate, microtasks, `Date.now` and `Math.random`. Timers must be created in the original's order, because ties run in creation order.
- Undefined becomes C# null or `double?`. JSON null is `JsonNull`. Where the original throws a TypeError, throw (`JsTypeError`).
- Constructor order: esbuild initializes class fields before parameter properties, after `super()`. Put anything with a side effect (timers, random numbers, reads of other fields) at the top of the C# constructor body.
- `Scripts/Runtime/Common/Generated/` (packets, opcodes, modules, constants) was generated once and is maintained by hand now. `CommonEnumsTests` compares it with `Tools/fixtures/out/common_enums.json`, so a protocol change updates both.

**Client (`Assets/PixelHero/Scripts/Runtime/`)** mirrors the original client module by module and keeps its names.
- `Network`: transports behind `IWebSocketTransport` (ClientWebSocket on PC, jslib on WebGL; events are dispatched on the main thread), `PacketFrames`, and `GameConnection` (the session up to Welcome).
- `Maps`: `ClientMap`, `RegionCache`, `TileDrawPlanner` → `MapView`. `MapCoords` is the **only** conversion between the original's coordinates (top-left origin, y down) and Unity's.
- `Entities`: `World` stands in for the original's `game`. `EntityPackets` holds the entity packet handlers. `EntityDrawPlanner`/`TextDrawPlanner` record draw commands, and `EntityCanvasRenderer` (with `Shaders/CanvasImage.shader`) and `UI/TextCanvasView` replay them, emulating the browser canvases. Draws are compared as recorded calls, never as pixels. `GameClient` forwards only `EntityPackets.Handled` to `EntityPackets.Handle`; add a new packet to both.
- `UI`: `UiKit` builds the original's HTML/CSS in uGUI code, in CSS pixels at integer scale. `Localization` loads `Localization/{ko,en}.json`; Korean is the default. `PixelText` uses Galmuri for Hangul.
- `Sprites/SpriteCatalog` indexes the imported assets. Frames are cut at run time.
- `Assets/PixelHero/Generated/` holds the imported assets and `SpriteCatalog.asset`. Scenes reference them by GUID, so move or replace them with their .meta files.

**Server (`Server/src/PixelHero.Server.Core`)** keeps the original's structure, names (fields stay camelCase, methods become PascalCase) and comments. Numbers are doubles, and JSON data keeps JSON shapes.
- Storage goes `IGameDatabase` → `GameDatabase` → `IDocumentStore` (`MemoryDocumentStore` for tests, `MongoDocumentStore` for the server). Game code never sees MongoDB types: the user plans to switch to PostgreSQL later. `DocumentStoreContractTests` run the same cases on every store.
- Keep MongoDB.Driver at **3.9.0**: 3.10+ refuses the user's MongoDB server, and 3.4–3.8 pull in vulnerable dependencies.
- The hub, HTTP API and Discord (`Network/Hub.cs`, `Network/Express.cs`, `Controllers/Incoming.cs`) are off unless `HUB_ENABLED`/`API_ENABLED`/`DISCORD_ENABLED` is set. While off, they must create no timer, socket or log line, so scenarios stay unchanged.
- Each simulated server in `ClusterHarness` has a `Realm` holding its per-server statics. Any new per-server static must be added to `Realm`.
- `Data/map_fixes.json` adds entities and object tiles missing from world.json (tutorial trees, shrimp spots, cooking pot). A change to it shifts startup instances, so `startup.json` and the scenario fixtures change with it.
- TLS: wss is served when `SSL_PORT` and `SSL_CERTIFICATE` are set (`Network/TlsCertificate`; .pfx or PEM + `SSL_CERTIFICATE_KEY`). The Unity client on an https page always connects with wss on 59443 (see `live.md`).

## Unity rules

- Use the new Input System only (`UnityEngine.InputSystem`), never `Input.*`.
- Game logic uses data grids, not Unity physics.
- A missing component is a fake null, so `GetComponent<T>() ?? AddComponent<T>()` never adds anything. Use `TryGetComponent`.
- `CommandBuffer.SetViewProjectionMatrices` already flips for render textures. Do not add `GL.GetGPUProjectionMatrix`.
- Blend modes are render state: give each canvas composite operation its own material (`EntityCanvasRenderer.CanvasMaterial`).
- In batch PlayMode tests, `WaitForEndOfFrame`/`ScreenCapture` don't work: render to a RenderTexture. Tests that inject input need `InputSystem.settings.backgroundBehavior = IgnoreFocus`.

## Secrets and environment

- `PixelHero-Data/.env` (gitignored) holds the local config, including the MongoDB connection; the database and its auth source are both `pixelhero`. `.env*.sample` hold a real `HUB_ACCESS_TOKEN`. Never print `.env` or sample values.
- dotenv keeps an inline `# comment` as part of the value, so never put a comment on a value line in `.env`.
- The server rejects a reconnect from the same IP within 5 s (`toofast`) unless `DEBUGGING=true`. This matters for automated connection tests.
- `SKIP_DATABASE=true` saves nothing and makes every player an admin, so admin chat commands (`/mob`, `/teleport x y`, `/kill`, …) work in scenarios. With the database on, admin commands need an account whose rank is set in `player_info`.

## Working with the user

- Communicate in **Korean**. Project docs are in Korean; CLAUDE.md stays in English.
- Plan large work in stages, each with an agreed way to verify it, and give a short report after each stage. If the user says not to start yet, only plan.
- Do **not** use browser automation or headless browsers. Write steps for the user to check in the browser instead.
- The user does all git operations (commits and pushes only on request).
